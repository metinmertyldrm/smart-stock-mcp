# Observability model

Smart Stock exposes several complementary signals. They answer different operational questions and should not be treated as interchangeable.

## Signal map

| Signal | Endpoint / source | Purpose | Authentication |
| --- | --- | --- | --- |
| Liveness | `GET /llm/api/health` | Is the HTTP process alive? | Public |
| Readiness | `GET /llm/api/ready` | Are the local conversation store and expected MCP connections initialized? | Public |
| Operational metrics | `GET /llm/api/metrics` | Request, chat and tool aggregates for this LLM-host process | Bearer session |
| Request correlation | `X-Request-Id` response header | Correlate one HTTP request with structured logs | Generated by server |
| Chat telemetry | `response.telemetry` | Execution/trace IDs, request ID and end-to-end duration for one chat operation | Returned with authenticated chat response |
| Execution trace | `response.trace` | Per-tool status, arguments summary, result summary and duration | Returned with authenticated chat response |
| Structured events | `docker compose logs llm-host` | Request lifecycle and rejected-session events | Host/operator access |

The normal Docker gateway is `http://localhost:5173`, so the table above uses the browser-facing `/llm` prefix. Inside the `llm-host` container the underlying paths are `/api/...`.

## Request correlation

`secure_api` creates a new opaque request identifier for every HTTP request. Caller-supplied request IDs are not trusted or reused.

The ID is returned as:

```text
X-Request-Id: <uuid>
```

For chat/confirmation responses that already contain the orchestration telemetry object, the same value is added to:

```json
{
  "telemetry": {
    "requestId": "..."
  }
}
```

The legacy `"HTTP request ID"` item is removed from `telemetry.missingFields` once correlation is attached.

This produces a useful chain:

```text
HTTP X-Request-Id
        |
        +--> structured http.request.* log events
        |
        +--> response.telemetry.requestId
                 |
                 +--> executionId
                 +--> traceId
                 +--> planId
                 +--> response.trace[*].toolCallId / mcpRequestId
```

## Structured JSON events

The observability logger emits one-line JSON messages for request lifecycle events. It deliberately does not include:

- request bodies,
- Authorization headers,
- bearer tokens,
- conversation message content,
- raw tool arguments/results.

Core events are:

- `http.request.started`,
- `http.request.completed`,
- `http.request.failed`,
- `security.session.rejected`.

Useful fields include `requestId`, normalized `route`, HTTP method, status, duration and exception type where applicable.

Conversation identifiers are normalized to `/api/conversations/{conversation_id}` before being used as metric/log route labels so a long-running process does not create one metric series per conversation.

## Liveness versus readiness

`GET /api/health` is intentionally shallow. A successful response only means the HTTP application can answer a request.

`GET /api/ready` is side-effect-free and checks local initialized dependencies:

- the agent exists,
- the SQLite conversation store accepts `SELECT 1`,
- all configured MCP server sessions are connected,
- at least one MCP tool has been indexed.

Readiness does **not** invoke Ollama, run an MCP tool, or perform a stock-service mutation. The Docker `llm-host` healthcheck uses `/api/ready`, so dependent containers do not start merely because the Python process opened a socket.

## Metrics schema

`GET /api/metrics` returns process-local JSON. It is behind the normal bearer-session boundary.

### HTTP

`http` contains:

- `totalRequests`,
- `activeRequests`,
- `serverErrors` for HTTP 5xx responses,
- route/method/status series with count, total latency, average latency and max latency.

Dynamic conversation IDs are normalized before aggregation.

### Chat

`chat` is populated from existing chat responses and contains:

- total/succeeded/failed counts,
- repaired-plan count,
- end-to-end duration sample count, total, average and max,
- bounded goal counts such as `INFO`, `PLAN`, `DRAFT`, `ORDER`, `RECEIVE` and `REASON`.

A semantically failed chat (`succeeded: false`) is counted even when its HTTP response is still 200, which is why HTTP status metrics and chat metrics are both necessary.

### Tools

`tools` is aggregated from the existing execution trace. Each series is keyed by tool name and execution status (`success`, `failed`, `skipped`) and includes:

- count,
- number of duration samples,
- total/average/max duration when available.

No raw tool arguments or responses are copied into the metrics endpoint.

## Verification workflow

After rebuilding the stack, first run the deterministic observability checks. They do not call Ollama:

```bash
python scripts/observability_smoke.py
```

That verifies:

- liveness responses contain `X-Request-Id`,
- readiness reports the conversation store and MCP topology as ready,
- metrics cannot be read without a bearer session,
- authenticated metrics aggregate the gateway requests.

Then exercise one real read-only chat:

```bash
python scripts/smoke_stack.py --chat
```

Finally require populated chat/tool aggregates:

```bash
python scripts/observability_smoke.py --expect-chat
```

The security smoke remains independent:

```bash
python scripts/security_smoke.py
```

## Operator troubleshooting

Inspect the current container state:

```bash
docker compose ps
```

Follow LLM-host logs:

```bash
docker compose logs -f llm-host
```

When a user-visible error includes or returns an `X-Request-Id`, search the LLM-host log stream for that same identifier. From there, use the response telemetry's `executionId` / `traceId` and the trace's tool-call identifiers to narrow the failing execution step.

A process can be **live but not ready**. In that case inspect `/llm/api/ready` first. A `conversationStore` error points to the local SQLite layer; an MCP `not_ready` state points to incomplete stdio MCP initialization.

## Limitations

TASK 08 intentionally starts with a dependency-free instrumentation contract rather than selecting an infrastructure vendor.

Current metrics are:

- in-memory,
- process-local,
- reset whenever the LLM-host process restarts,
- not a Prometheus text endpoint,
- not persisted time-series data,
- not distributed tracing across independent services.

If the host later runs multiple workers, an external metrics/tracing backend will be required to aggregate processes correctly. The current schema is designed so a Prometheus/OpenTelemetry exporter can be added around the registry without changing the orchestration response contract.
